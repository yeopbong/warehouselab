# Planning and motion semantics

`src/core/planning` implements static A* and prioritized time-space A* independently of the UI. Grid coordinates are integers; station bodies and obstacles are blocked, while service cells are ordinary walkable cells. Paths contain future positions, excluding the current position. A repeated position is a real wait action.

Each kernel tick passes a single snapshot and a goal map to `planRobotMoves`. Missing goals mean stationary robots. The planner returns every robot's next position without changing current positions; the kernel commits these positions simultaneously. The planner consumes the first path cell, leaving the remaining future path for planning reuse. A planned path is not an executed motion trace. Only `path`, `pathPlannedAt`, serializable `planner` reuse metadata, and the additive diagnostic `planningMs` are mutated.

The reservation table records owner IDs for vertices at arrival times and directed edges between consecutive times. A move checks destination occupancy and the reverse edge, preventing vertex collisions and swaps. Reaching the end of a short path reserves that endpoint for the rest of the horizon. Before planning, every robot holds its current position through the entire horizon. In priority order, the planner releases only that robot's reservations and atomically inserts its new path. Other robots' reservations cannot be overwritten. This conservative treatment includes waiting, loading, unloading, idle, unreachable, and not-yet-planned robots; none are assumed to disappear.

Fixed priority sorts robot IDs. Waiting priority sorts descending current consecutive `waitTicks`, with robot IDs breaking ties. All search ties and neighbor ordering are stable. Neither robot array traversal order nor elapsed wall time determines a movement decision.

Time-space search includes four cardinal moves and a wait. Each action costs `1 + congestionWeight * density(destination)`, where density is the observed count of robots at that cell plus half the count at its four adjacent cells. Both terms are nonnegative. Distance routing sets the extra cost to zero. Kernel 1.1.0 uses a reverse breadth-first distance field from the goal through static walkable cells. Its unit-edge distance remains an admissible, consistent lower bound with nonnegative congestion costs. Congestion changes route preference only. It does not change reservations, service rules, or robot speed, and observes no future orders.

Within the bounded window, a goal is accepted only if it can remain reserved through the end of the window. If the goal is too far away or currently occupied, the search chooses a reachable endpoint at exactly the horizon with the lowest remaining **static route distance**, then lowest accumulated routing cost, then stable search order. Static distance supports obstacle detours that must initially increase Manhattan distance. The 20×20 regression, with walls at x=10/y=1…18 and a robot travelling (9,10)→(11,10), follows the legal 20-step route with windows 4, 12 and 16. A statically unreachable goal returns no route and the robot retains its real occupancy.

Distance fields are derived data cached by exact dimensions, sorted blocked-cell topology and goal. An obstacle or station-body change selects a new key immediately, including in-place edits. Least-recently-used eviction caps the cache at 64 fields and 102,400 cells; an oversized field is computed without caching. No timing, eviction order or cache hit changes the returned distances. Static reachability supplies a lower bound, never permission to bypass live reservations.

The resulting safe partial path advances under rolling replanning. This is a local progress rule, not a multi-robot completeness or deadlock-freedom guarantee: narrow passages, opposing traffic and occupied service cells can still cause waits or deadlock. Unplanned robots' conservative holds can also reduce throughput. The simulator retains these states rather than removing robots or changing the map.

The configured replan interval controls actual A* calls. A remaining path is reused before the next interval only if its goal, policy configuration, geometry, and reservations are still valid. Goal/configuration changes, exhausted paths, topology edits or reservation conflicts force an immediate new search. The window can change between ticks without bypassing validation. Owner reservations are rebuilt relative to each current snapshot; stale absolute times cannot survive a tick. Path-reuse metadata is part of `SimState.planner`, bounded by the current fleet, and included in the deterministic digest. `structuredClone` and JSON checkpoints preserve reuse decisions; restoring a checkpoint does not silently force extra replanning. Semantic planner state must remain inside the snapshot for deterministic checkpoint replay. Wall-clock planning totals remain excluded from the digest.

Finally, `validateSimultaneousMoves` holds conflicting movers and repeatedly propagates holds to robots that would enter a now-stationary robot. It rejects illegal steps, destination conflicts, swaps, and entry into stayers. Following a robot that actually leaves is legal. Physical validation is a hard constraint, never an optimization penalty. Wall-clock planning duration is diagnostic and has no effect on search, priority, random seeds, or simulation time.

## Delivery order priority and demand

Delivery transport needs are globally sorted by order arrival tick, then stable order ID. An older order at `z-delivery` therefore precedes a newer order at `a-delivery`. An order without available source stock, destination capacity or a statically connected source/eligible robot is skipped; it does not block other executable needs. The same bounded obstacle-aware BFS field checks robot, source service and destination service connectivity; dynamic traffic reservations remain authoritative. Reservations commit immediately. Assembly inputs then process inputs retain their downstream-first generation and deterministic station/source ties. This order/task priority is independent of **robot priority**, which controls whose motion is planned first.

`oldestUnfinishedAge` is `current tick − arrival tick` for the oldest arrived unfinished order, including reserved or partly delivered orders; it is `null` when none remain. Future orders do not inflate the backlog age. Completed-order delay metrics remain separate, so stalled old demand cannot disappear from the reported latency picture.

The first three presets use finite order batches; the held-out map is `PRESETS[3]`. The named `SUSTAINED` preset (`PRESETS[4]`, `scenarios/sustained-production.json`) has twelve robots, three production cells and two dispatch stations. It generates 2,000 orders before the run using seed 512, five-tick intervals and bounded seeded arrival jitter. For the documented 600–1,200 tick observations, orders continue throughout the horizon and backlog remains observable. The stream is finite, with its final arrival around tick 9,995. There is no warm-up: throughput counts all orders completed within the observation horizon divided by its ticks, and backlog age uses every arrived unfinished order. Every compared method must use the same scenario, order seed and horizon.
